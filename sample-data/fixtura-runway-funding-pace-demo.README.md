# Fixtura "Runway funding-pace demo" data set

Generated by Fixtura (si2026-test-generator) to exercise Runway's **funding-pace
tripwire (#22)** — the amber *"Funding due"* state. This is the contract that
should **not** cry wolf: it is incrementally funded and its **funded dollars**
run dry before the period ends *while the ceiling still holds and funding is
keeping pace with the burn*. That is routine incremental funding awaiting its
next mod, not an over-ceiling breach — so it reads amber, never red.

What makes this the sharp #22 case: funding is **62% obligated at ~69% of the
PoP elapsed** — funding is *behind* the clock, so a naive ceiling/elapsed check
would scream red. But the obligations are *landing* as fast as the dollars burn
(the SF-30 mod history proves it), so the engine holds it at amber.

Sibling to `fixtura-runway-burn-demo.*`. One coherent contract across all files
(same seed ties them).

## The obligation history (what the mods rebuild)

The SF-26 award carries only the **initial** obligation. Funding pace comes from
the **SF-30 modifications** — ingest them one at a time at
`POST /api/contracts/{id}/mods` to reconstruct the dated history:

| Action | Effective | Amount | Cumulative obligated |
|---|---|---|---|
| Award                        | 2025-11-18 | $1,927,000.00 | $1,927,000.00 |
| P00001 — option exercise     | 2026-03-17 | $1,211,000.00 | $3,138,000.00 |
| P00002 — incremental funding | 2026-07-28 | $1,266,093.35 | $4,404,093.35 |

Ingesting both SF-30s reproduces `total_obligated = $4,404,093.35` exactly, and
re-ingesting a mod is idempotent (dedup by mod number — no double-counting).

## Expected result (funding-aware engine, #22)

Both labor CLINs read **amber `funding` ("Funding due")**, not red:

| CLIN | Title | Funded | Funds run out | vs. PoP end |
|---|---|---|---|---|
| 0001 | Cybersecurity Support     | 62% | ~wk 47 | before wk 52 |
| 0002 | Operations & Maintenance  | 62% | ~wk 49 | before wk 52 |

Why amber and not red: the funded slice runs out ~wk 47–49 (before the PoP ends
at wk 52), **but** projected spend does *not* blow the full $7.07M ceiling before
PoP end, and the obligation history shows dollars landing **at or above** the
burn rate (~$122k/wk obligated vs. burn) — so `funding_pace_source` is
`obligation_history`, not the proxy. The engine flags "next funding mod needed,"
never "over ceiling." Contract-level `all_clear` is false (there is an
advisory), but no red tripwire fires.

## How it was generated (reproducible)

Fixtura preset generation, **seed 19**. The award (`govcon_award_sf26`) and
`govcon_contract_data` use:

```json
{ "pop_in_progress": true, "option_years": 0, "contract_type": "T&M" }
```

The timesheet / labor exports (`govcon_timesheet`, `govcon_labor_export`) add
`"staffing": 1.0` so the roster is crewed to the plan and burns on plan. The
SF-30s are rendered one per obligation-history mod (the `govcon_mod_sf30`
mapping, with the history truncated to each successive action).

> Note: this bundle deterministically reads amber only because Fixtura's
> timesheet weeks now span the **whole** elapsed PoP (not just a trailing
> ~25-week window). Before that fix a PoP older than ~25 weeks left an unlogged
> gap at the front and Runway's `current_week` was ambiguous. See the Fixtura
> repo's `_recent_week_ending`.
